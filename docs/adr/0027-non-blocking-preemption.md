# ADR-0027：抢占不阻塞 —— 被抢占的 run 在后台排干，期间的请求只留最新一个

- 状态：已采纳
- 日期：2026-10-01

## 背景

D3（m2-plan）定的是「同一时刻一个活跃 run，新 run 抢占旧 run」，实现是 `RunManager::start` 里同步 `cancel + join` 旧 run。
bridge/README 当时写下了代价：旧 run 卡在不可取消的算子里时，这个 command 会等它跑完。没写出来的是**这个 command 在哪个线程上等**：

- `run_graph` 是同步的 `#[tauri::command]`。tauri-macros 为同步命令生成的代码在 IPC 处理器里直接调用它，
  而 wry 的 WebView2 后端在 UI 线程上派发 IPC 请求 —— 它就在主线程上执行；
- 全仓只有 std-pointcloud 的两个算子声明了可取消。OpenCV、PCL、onnxruntime 的一次调用进去就出不来。

点云没暴露，是因为预览把输入抽到 20 万点，每个节点都快。图像没有抽稀（ADR-0011 只认点云），
真 app 里抢占一次正在跑 `image.find_circle` 的运行（1280×960）：主窗口的消息循环停了约 7.5 s，第 5 秒起 Windows 判它「未响应」，
同期一个最轻的 IPC 排了 8.4 s（docs/large-image-plan.md §0）。

## 决策

1. **`run_graph` 里不再 join。** 有 run 在算时，取消它、挪进 `draining`，新请求排进 `pending`，立即返回新 runId。
2. **同一时刻最多一个 run 在算。** `draining` 退出之前再来的请求顶掉 `pending`，只留最新一个；`draining` 退出时由它的收尾线程启动 `pending`。
3. **排队中的请求作废时补发 `run_finished`。** 被 `cancel` 取消、被 `stop_active` / `drop_all` 清掉的补发 `cancelled`；
   启动失败（core 返回空句柄，只在内存不足时）补发 `error`。被新请求顶掉的不补发。
4. **`run_graph` 照旧是同步命令**，不改成 async。
5. 重扫库目录（`stop_active`）与热重载（`drop_all`）**仍然等**被抢占的那个退出。

## 理由

**为什么要限到「最多一个在算」，而不是被抢占的就让它自己在后台算完、新的立刻开跑。**
编辑器拖参数时每停顿 30 ms 就发一次预览（`lib/preview.ts`），一秒好几次。新的立刻开跑的话，每次抢占都留下一个停不下来的计算：
拖一会儿就是十几个霍夫变换同时在算，各自握着整张图的中间结果，CPU 和内存一起失控。
排队只留最新一个，代价是被抢占的那个还没算完时，新结果要等它 —— 但界面一直能动，而用户要看的本来就是最后一次的参数。

**为什么不改成 async 命令。** async 命令跑在线程池上，命令之间就不再串行。重扫库目录是「先停掉所有 run，再重建注册表」，
它靠的正是主线程上的串行：两步之间不会插进一次 `run_graph`。保持同步命令、只去掉里面的 join，串行和不阻塞都保住了。

**为什么被顶掉的请求不补发 cancelled。** 发起方（前端）手里已经是更新的 runId，只认最后发起的那次；
补一条 cancelled，前端在拿到新 runId 之前先收到它的话，工具栏会闪一下「已取消」。真正等着这个 runId 收场的只有「取消」这一种情形。

**为什么事件顺序的保证可以丢。** 以前同步 join 保证「前端拿到新 runId 时，旧 run 的 `run_finished(cancelled)` 已经发出去了」。
前端本来就按 runId 分流事件，对不上的当孤儿暂存、下一次 `beginRun` 清掉 —— 晚到的那条无害，这条保证没有人真正依赖。

## 代价

- 被抢占的 run 算完之前，新请求开不了跑：拖一个慢算子的参数时，结果要等上一次算完。界面不卡，但不更快 ——
  让慢算子本身变快是图像预览按比例缩小的事（ADR-0028）。
- 排队的请求要自己持有一份图 JSON 与注入数据（`RunInput` 的缓冲），拷贝只花在真要排队的那一次。
- 重扫库目录仍会等停不下来的算子算完，那段时间窗口是卡的。它是显式的、少见的操作，注册表重建的正确性比它重要。

## 不做

- 能在 OpenCV / PCL 调用中途停下来的取消：做不到。
- 放弃（detach）卡住的工作线程：它握着结果仓里的数据和 DLL 的引用，放掉它比等它危险得多。
