# ADR-0011：live preview 是一次抽稀过的普通 run

日期：2026-09-06（M4）　状态：已采纳

## 背景

architecture.md 把 live preview 称作「体验的分水岭，也是最容易做错的一块」，
并要求 C++ 侧支持**可取消**和**降级质量**。M2 已经把「可取消」做成了 run 的形态
（抢占式：新 run 取消旧 run），剩下的就是「降级质量」。

最直觉的做法是给算子加第二套 `preview()`：每个算子自己决定怎么少算一点。
十六个算子就是十六份新代码，而且每一份都要单独验证「预览和正式的结果趋势一致」。

## 决定

**preview 是一次 `mode=preview` 的普通 run，唯一的区别是：无输入的源算子的输出
在存进结果仓之前先做等步长抽稀。其余算子一行代码都不改。**

- run 选项加三个字段：`mode`（full | preview）、`previewMaxPoints`（默认 200 000）、
  `previewBudgetMs`（默认 300）。C ABI 升到 v5，结构体末尾追加，不改形态。
- 「源算子」的判据是**这个节点没有输入边**，不是算子自己声明的 capability。
  load / synthetic / 将来的库源节点自动都算，加新算子不用记得配什么。
- 抽稀走 `PointCloud::select`，所以 intensity / normals / rgb 一起被搬走，
  下游算子拿到的仍然是一片形状正常的点云。
- （2026-10-01 补）图像在源头按 2 的幂缩小到 4 MP 以内；缩小改变了像素量的尺度，所以执行器替下游换算
  像素参数与像素几何 —— 算子照旧不知道自己在预览（[ADR-0028](0028-image-preview-pixel-scale.md)）。
- **cacheKey 混入 `preview:<maxPoints>`**：预览结果与正式结果互不命中，
  互不淘汰对方（都在同一个 LRU 里，但键不同）。
- 超过 `previewBudgetMs` 的 run 发一条 `log warn`，前端据此提示「降低预览点数」。

## 后果

**抽稀在源头一次生效，全链路自然变快。** 一条十节点的链，源头从 400 万降到 20 万，
后面每一个节点都跟着快二十倍 —— 不需要它们知道自己在预览。

**「预览过的图」和「正式跑过的图」在缓存里是两份。** 内存占用因此翻倍（上限仍然由
LRU 预算管着）。换来的是「松手之后正式结果替换预览」不需要先清缓存，
也不会出现「正式运行拿到了抽稀过的结果」这种最坏的静默错误。

**`cancellable=false` 的 PCL 算子在预览下无碍。** 输入已经被抽到 20 万点，
单个节点的耗时可控；真正要取消的场景（拖动时连发）由抢占解决 ——
新 run 会 cancel 旧 run，而旧 run 在下一个节点边界退出。

**预览结果是抽稀过的，不能当结论。** 前端在 3D 视图上打一个「预览 20 万点」的角标，
松手之后按「自动运行」开关补一次正式 run。这个开关默认开着；关掉它的人是在明确说
「我知道我看的是预览」。

**preview 只跑到选中节点。** 前端发的是 `targets=[选中节点的路径 id]`，
不是全图 —— 拖参数时用户看的就是那一个节点的输出，把整张图跑一遍是白费的。

> 修订（2026-10-03）：用户看的不一定是改的那个节点 —— 预览钉在下游（最后的测量、裁出来的那片云）时去拖上游的阈值，
> 只算改的节点的话画面一动不动。现在 targets 是改的节点，再加上**在它下游的**预览节点（钉住的，没钉就是选中的 ——
> 参数面板里改别的节点时选中不变）与对比里没冻结的 B（`lib/nodeRun.ts` 的 `previewTargets`；看着的在外面几层时，
> 从包着改动的那个子图节点往下游找）；不在下游的不带。松手后补的那次正式 run 用同一组 targets。

> 修订（2026-10-04，用户拍板）：**自动运行管所有改参数的方式**，不只是拖动松手。敲回车、下拉框、勾选框、取色器停手、
> ↺ 重置、右键粘贴值 / 全部恢复默认、「恢复这组参数」、调参页的 ↩、撤销 / 重做 / 跳到历史某一步 —— 提交了一步（graph store 的
> `onCommitted`：记进撤销栈的那一下与撤销 / 重做；拖动的中间帧、没改动的 commit、换图不算），参数的有效值、静音或图参数的取值
> 变了（`lib/autoRun.ts` 的 `paramEditTargets`；挪节点、改名、增删节点、连线这些结构上的改动不算，谁提供参数变了 —— 纳入配方、
> 绑定、提升 —— 也不算，那是值搬家），就攒 250 ms 补一次正式 run（连按方向键、连按几次撤销只跑一次），targets 与拖动松手同一条
> 规则（改的节点加上它下游正看着的）。只补跑过的节点：从空白开始拼、新接的分支还没跑过时不替人开第一次（与 2D 拖框、切配方同一条）。
> 人点的运行（F5、▶、运行到这里）开跑前撤掉攒着的那一次 —— 它读的就是现在的图，不撤的话过一会儿会把人点的这一次抢占掉。
> 拖动松手照旧由 `endPreview` 补（commit 那一下还在预览态，`onCommitted` 不重复补），攒着的改动并进那一次。关掉「自动运行」
> 就回到以前：只拖动时看抽稀的预览，F5 才正式跑；这时「改 N 处」攒得下来。

## 备选方案

**每个算子实现 `preview()`。** `Capabilities::previewable` 这个字段从 M0 就在
manifest 里留着，本来就是为它准备的。拒绝的理由是成本乘以算子数量，而且「体素栅格的
预览版」是什么根本没有唯一答案。这个字段留着，将来某个算子真有更聪明的降级方式时再用。

**限时中断（跑够 300 ms 就停）。** 结果会随机器负载变化，同样的参数两次看到不一样的
东西，用户会以为数据在抖。而抽稀是确定性的：同一份输入、同一个 maxPoints，
两次预览逐点一致。

**复用正式缓存（不分命名空间）。** 省内存，但会让「预览之后正式运行直接命中了抽稀的
结果」成为可能 —— 这是一个静默给出错误结果的路径，是本项目最不能接受的一类 bug。
