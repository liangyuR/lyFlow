# ADR-0009：热重载靠「复制一份新 DLL 再加载」，缓存随之清空

- 状态：已采纳
- 日期：2026-09-06

## 背景

加一个算子的完整流程是「在 C++ 里注册 → 重启」（ADR-0003）。那个「重启」在 M0–M2
是可以忍的，因为一次迭代本来就要等 C++ 编译。到 M3 就不行了：调一个算子的参数
范围、改一句 doc、加一个端口，每次都要关掉 app、丢掉画到一半的图、重新摆一遍数据，
反馈循环从秒级掉到分钟级。

ADR-0004 已经把 core 做成运行时加载的 DLL，`Core` 里是一张函数指针表。
理论上「丢掉旧表、加载新的」就完了。实际上有两个硬约束：

1. **Windows 锁住已加载的 DLL 文件。** 只要 `lyflow_core.dll` 还被映射着，
   CMake 的链接器就写不进去 —— 构建直接失败，连热重载的机会都没有。
2. **缓存里的 `Data` 是旧 DLL 里的对象。** `shared_ptr<const PointCloud>` 的
   析构函数、vtable、分配器全在旧模块的地址空间里。旧 DLL 一卸载，这些指针就是野的。

## 决策

**E4：热重载 = 丢掉旧的 `Arc<Core>` → 把新 DLL 复制成 `lyflow_core.gen<N>.dll` → 加载它。
缓存随之清空，接受。**

一轮换代的顺序是死的：

```
取消活跃 run → 放掉全部 RunHandle → 清空结果仓 → 复制 → 加载 → 自检 → 换掉 Arc<Core>
```

- 监视的是 `build/core/bin/lyflow_core.dll`（`scripts/core-watch.ps1` 的产物）。
  这个路径由 `env!("CARGO_MANIFEST_DIR")` 推出来，安装包里不存在 → watcher 不启动。
- 复制的目标带代号：`lyflow_core.gen1.dll`、`gen2.dll`……**旧代的文件删不掉是常态**
  （自己还锁着），所以清理放在**下一次启动**时做一遍。
- 自检（`manifest_problems` 为空 + manifest 是合法 JSON）不过就**保留旧代**，
  emit `core-reload-failed` 附问题列表。
- 成功则 emit `manifest-updated`，前端整份替换 manifest store，**当前 doc 一个字不动**；
  算子消失的节点在画布上显示成「算子缺失」，可删可等。
- 依赖 DLL（PCL、boost）不参与热重载。它们不是我们改的东西。

## 理由

**为什么必须复制。** 不复制的话第一次热重载之后 CMake 就再也构建不了了 ——
功能上线第一天就把自己锁死。复制一份的代价是几十毫秒和一个临时文件，
换来「构建和运行互不打扰」。

**为什么代号而不是固定的第二个名字。** 固定名（比如 `lyflow_core.hot.dll`）在第二次
热重载时同样被锁着。自增代号让每一代都有自己的文件，代价是要清理 —— 而清理只能
在下次启动做，因为当前代永远是锁着的。

**为什么缓存必须清空，而不是「想办法保住」。** 结果仓里存的是 `shared_ptr<const PointCloud>`。
跨模块持有它意味着：旧 DLL 的代码段要一直留着（那就没「卸载」可言），
或者把数据深拷贝到一块中立的堆上（那要给每种 `Data` 写一套序列化，
而且新旧两版的 `PointCloud` 布局可能已经不一样了）。
两条路都比「重跑一次」贵得多，而热重载发生在**开发期**，重跑一次是完全可接受的。

**为什么自检失败要保留旧代。** 半坏的一代比旧的一代难查十倍：界面上的算子是新的，
行为是旧的，或者反过来。启动时的自检已经是 fatal（`bridge/src/lib.rs`），
热重载沿用同一条判据，只是把「退出进程」换成「不换代 + 说清楚为什么」。

**为什么是 `notify` 而不是轮询。** 轮询要在「响应快」和「不烧 CPU」之间选，
而链接器写 DLL 是一串事件不是一次 —— 无论如何都要 debounce。既然 debounce 跑不掉，
就用一个真正的文件监视器，把 400 ms 的安静期用在刀刃上（等链接器写完）。

## 一个容易漏的前提

**`Arc<Core>` 的引用计数必须真的归零。** `RunHandle` 持有 `Arc<Core>`，
`RunManager` 又持有正在跑的和上一次完成的两个 `RunHandle`。
换代前不调 `RunManager::drop_all()` 的话，旧 DLL 只是「换了个新的顶上」而不是被卸载，
两代同时活着，而结果仓是两个不同的单例 —— 症状会非常离奇。
所以 `watcher::reload` 里那个顺序不是风格问题。

## 代价

- `core()` 从 `OnceLock<Arc<Core>>` 变成 `RwLock<Result<Arc<Core>, String>>`。
  每次调用多一次读锁，可以忽略；但「进程内 core 只加载一次」这条不变式没了。
- manifest 的解析缓存要按代数失效（`commands.rs` 的 `MANIFEST` 现在存 `(generation, value)`）。
- 热重载中途正在跑的 run 会被取消。这是有意的：它跑的是旧代码，结果留着只会误导。
- 只在开发期可用。安装包里 `watch_source()` 返回 `None`，watcher 不启动，
  代数永远是 0 —— 状态栏据此决定要不要显示那个标记。

## 复议条件

如果将来 core 变成一个独立进程（headless 与 GUI 分离），热重载就不再是「换函数表」
而是「重启子进程」，这套复制 + 代号的机制会整个作废 —— 但那时候连 ADR-0004 都要重议。
