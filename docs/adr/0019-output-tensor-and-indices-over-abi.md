# ADR-0019：张量与下标集合经 C ABI 按切片取出，解释权留在前端

- 状态：已采纳
- 日期：2026-09-13

## 背景

连线内容查看器（[edge-peek-plan.md](../edge-peek-plan.md)）要做到「双击一条边，看见这条线上流的东西」。
十三个端口类型里，十一个已经能看：点云走 ADR-0006 的二进制通道，其余九种的完整 JSON
随 `node_state` 事件早就到了前端。

剩下两个**根本取不出来**：

- `Tensor`：`Data::valueJson` 只写 shape、count、min/max/mean，张量本身从不进 IPC（ADR-0015 的 T7）。
- `Indices`：声明上走二进制通道，但 `ResultStore::previewCloud` 一上来就 `data.asCloud()`，
  对 Indices 返回 false —— 通道从来没接上过。

于是「Tensor 当图像看」「Indices 看得见」两件事都是空话。要补，摆在面前的是三条路：

1. 后端把张量**渲染成图像字节**返回，前端只负责 `<img>`；
2. 后端返回**原始 float + 形状**，前端自己决定布局、通道、归一化与色带；
3. 把张量塞进 `valueJson` 走 JSON（与点云当年那条死路同构，不予考虑）。

## 决策

**C ABI v7 → v8，新增两对入口，返回原始数据 + 完整形状，按 `offset/count` 切片。**

```c
LYFLOW_API int lyflow_output_tensor(const char* run_id, const char* node_id, const char* port,
                                    uint64_t offset, uint32_t count, lyflow_tensor_view* out);
LYFLOW_API int lyflow_output_indices(const char* run_id, const char* node_id, const char* port,
                                     uint64_t offset, uint32_t count, lyflow_indices_view* out);
```

配套四条约定：

- **`shape` 永远给完整形状**，不随切片变 —— 前端要靠它算下一片在哪。
- **张量不抽稀**。数据量靠切片控制，桥接层把一次请求 clamp 到 16 MB。
- **零拷贝借用**：`handle` 里放一份 `Data` 的浅拷贝（内部是 `shared_ptr`）保活，
  数据指针直接指进结果仓里那一份。
- **`offset` 越界返回成功 + 空切片**，不是错误。

**布局的解释权在前端**：`(H,W)` / `(H,W,C)` / `(C,H,W)` / `(N,H,W,C)` / `(N,C,H,W)` 由前端按
末维与首维的大小推断，猜错了用户在下拉框里改。色带、归一化范围、通道选择同理，全在前端。

## 理由

**为什么不是后端渲染成图像（路 1）。**
看一张特征图的人，一秒钟要改一次归一化范围、翻一次通道、换一次色带。
每一下都走一趟 IPC 是不可接受的手感；更要命的是那等于把「怎么显示」钉死在 C++ 里 ——
色带表、`NaN` 怎么画、通道怎么映射，这些是显示策略，不是算子契约。
ADR-0003 已经立过同一条规矩：C++ 给事实，前端给呈现。

**为什么张量不能像点云那样抽稀。**
点云抽稀是保形的：等步长拿走十分之一的点，形状还是那个形状（`previewCloud` 的注释里
写过为什么是等步长而不是随机）。图像抽稀不是 —— 隔行取样得到的是**另一张图**，
而人正是在看那些细节。所以张量这边用切片而不是抽稀：给你完整的一片，而不是残缺的全部。

**为什么零拷贝借用，而点云是复制。**
点云那条路必须抽稀，抽稀天然产出一个新缓冲，复制是顺带的。
张量切片是内存里一段连续区间，没有任何理由复制 —— 一张 1024×1024 的特征图是 4 MB，
复制一次就是白白多 4 MB 和一次明显的停顿。`handle` 持 `Data` 的 `shared_ptr` 拷贝就够保活了。

**为什么 Indices 只给下标数组，不在 core 里实体化成点云。**
`Indices` 只带一个 `sourceCloudId`，它指向哪片云是上游图的结构决定的，
要 core 去回溯那条边，等于让结果仓认识图 —— 层次全乱。
而且「把选中的点在上游云上高亮」才是真正有用的展示，那是前端把两份数据合成出来的东西，
不是一个新的数据类型。本轮只做文本列表，高亮留给以后（计划 §8）。

**为什么越界不是错误。**
翻页翻到最后一片、切片器停在边界上，这是正常操作而不是错误路径。
返回 `count=0` 让前端一个分支就处理完，返回错误码会逼出一堆「这个错该不该弹提示」的判断。

## 代价

- **ABI 版本跳到 8**：嵌入宿主要重新对一次头文件（`client.hpp` 的 `kClientAbiVersion` 自动跟随）。
  这是 v7 之后第一次跳版本，加的是纯增量入口，老符号一个没动。
- **HTTP 参考实现（`packages/editor/test-server/`）覆盖不到这两个端点**：
  那个桩服务器每次请求都起一次 `lyflow` CLI，没有常驻的结果仓，点云能work 是因为 CLI 有
  `dump` 能写出 PCD 文件，而张量与下标没有对应的落盘格式。两个端点在桩里返回 501，
  契约文档上照实写明。真正的业务服务（阶段 B）按 ABI 直接实现，不受此限。
- 前端多了一处「猜布局」的启发式。猜错的代价是用户改一次下拉框，不是错误数据 ——
  形状始终是后端给的真值。

## 不做

- 后端渲染图像、后端做归一化与色带；
- 张量抽稀 / 降采样预览；
- Indices 在上游点云上高亮（前端合成，以后再说）；
- 保留历史 run 的结果以便回看：桥接层只留最近一个已完成的 run 句柄，
  旧 runId 的索引在新 run 开始时就被 `freeRun` 抹掉。
  这条约束直接决定了查看器的「锁定快照」只能冻结前端已解码的数据，
  理由与取舍见 [edge-peek-plan.md §4.5](../edge-peek-plan.md)。
