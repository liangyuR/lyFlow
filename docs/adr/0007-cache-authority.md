# ADR-0007：缓存复用的判定只在 C++，前端只读结论

- 状态：已采纳
- 日期：2026-09-06

## 背景

M3 要让「原图重跑」几乎不花时间，也要让用户看得见「哪几个节点真的会重算」。
两件事其实是同一个问题：**谁有资格说某个节点的结果还有效？**

前端手里有整份 GraphDoc，看上去完全可以自己算一个哈希：
op id + 版本 + 参数 + 上游的哈希。M1 甚至已经有一份类似的东西
（运行后图有任何改动就整体标 stale）。诱惑很大 —— 不用过 IPC，还能即时响应。

## 决策

**E1：缓存复用的判定只在 C++。** 具体是三条：

1. `cacheKey` 由 `exec::buildPlan` 计算，前端不参与、不复算、不猜。
2. 前端通过新的 `lyflow_plan` 拿到每节点
   `{ nodeId, cacheKey, cached, level, upstreamMissing, bypass }`，
   与上一次 `run_started.nodes[].cacheKey` 对比来标 stale。
3. 结果仓 `freeRun` 不再顺手删 Data；生命周期改由 **LRU 字节预算**管，
   默认 `min(8 GB, 物理内存 40%)`，正在跑的 run 用 `CachePin` 把自己的键钉住。

C ABI 因此多三个入口：`lyflow_plan`、`lyflow_cache_clear`、`lyflow_cache_stats`。

## 理由

**前端算不出 `externalKey`。** `io.load_pcd` 的结果是否有效，取决于磁盘上那个文件的
`size:mtime`——路径一个字没改，文件被覆盖了，缓存就必须失效（ADR-0006 留的钩子）。
前端没有那个信息，也不该有：它要么去读文件（越界，而且慢），要么假装文件没变
（错，且错得很安静 —— 用户会看着三小时前的点云调参数）。

**「差不多对」的哈希比没有哈希更糟。** 缓存判定错一次的代价不是慢，是**结果是错的**，
而且没有任何提示。两份实现只要有一处不同步（参数规范化的浮点写法、上游端口的排序、
不确定性算子的处理），就会长期给出静默的错误答案。一份实现只会「慢一点」。

**它本来就是 C++ 的职责。** architecture.md 的分工表里，「中间结果缓存与复用」在核心层，
「执行调度」也在核心层。前端那一栏明确写着**不负责**内存管理。
让前端去推缓存等于在这条线上开一个洞。

**为什么不干脆让前端每次都问一遍 `lyflow_validate`。** `validate` 不算 cacheKey，
也不看结果仓。真要复用它就得让它多返回一堆东西，那它就是 `lyflow_plan` 了 ——
不如给一个名字诚实的新入口。

## 落地时的三个细节

**没有输出端口的算子永远不复用。** `io.save_pcd` 的全部意义就是副作用。
按 cacheKey 跳过它，表现是「运行成功了但文件没写出来」，是最坏的一类「优化」。
判据写成 `op->outputs.empty()` 而不是维护一张黑名单：没有输出的算子，
它存在的理由必然在函数体外面。

**`bypass` 进 cacheKey。** 静音改变的是结果本身（ADR-0008 之外的另一条 E5），
不进键的话「静音 → 跑 → 取消静音 → 跑」第二次会拿到静音时的结果。

**pin 不是可选的。** LRU 是全局的，一次运行里上游先算完、下游还没读，
中间要是来一个大节点把预算撑爆，上游的结果就会被淘汰掉，
下游读到「上游没有产出结果」。所以每次运行开始就把计划里所有键钉住，
`CachePin` 析构时解钉。全被钉住时宁可暂时超预算 —— 正在算的那份不能扔。

## 代价

- 多一次 IPC。用 150 ms 的 debounce + 一个 ticket（晚发的赢）压住频率，
  拖滑块时不会每帧编译一次。
- 图当前不合法时 `lyflow_plan` 返回的是诊断而不是计划，前端此时没有 stale 信息。
  这是对的：一张连不通的图，「哪些节点会重算」本来就没有答案。
- 结果仓不再随 run 结束而缩小，常驻内存变成预算那么大。
  状态栏显示占用、菜单里有「清空缓存」，让它可见、可控。

## 复议条件

缓存落盘（跨进程持久化）会推翻这里的一部分：那时 `cached` 的判定要多一层
「磁盘上有没有」，而 LRU 要变成两级。m3-plan §5 明确不做，`externalKey`
与内容寻址的键定义已经为它留好了口子。
