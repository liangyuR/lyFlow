# ADR-0003：算子描述由 C++ 侧导出

- 状态：已采纳
- 日期：2026-09-05

## 决策

算子描述（名称、分类、输入输出端口及类型、参数定义含范围和默认值）从 C++ 侧生成，
Rust 转发给前端。前端不硬编码任何算子知识。

**加新算子只改 C++，前端零改动。**

## 理由

算子数量会长到几十上百个。如果每加一个算子都要同步改前端，那么：

- 前后端会持续不一致（改了 C++ 忘了改前端，参数范围对不上）
- 加算子的边际成本恒定不降，会直接抑制算子的增长
- 前端仓库会积累大量与自己无关的领域知识

把描述放在算子定义旁边（C++ 的注册宏里），单一真实来源，编译期就能保证一致。

**这一条做对了，后面加几十个算子都很轻松。** 它的收益会被乘上未来所有算子的数量，
所以在 M0 就要做，不能推迟。

## 前端唯一需要知道的算子知识

`param.type` → React 控件的映射表（见 [operator-manifest.md](../operator-manifest.md)）。
新增一种参数类型的成本是前端加一个 case，这是可接受的、有界的。

## 后果

**正面**

- 加算子无需前端参与
- 支持热重载：C++ 重编译后推一次全量 manifest，前端刷新面板，当前图不重置
- headless 执行和 UI 执行共享同一份算子定义与校验

**负面**

- C++ 侧要维护描述元数据，注册宏会变复杂
- 描述的表达能力受限于格式设计。有意保持克制：`visibleWhen` 只支持简单等值判断，不做通用表达式引擎；
  端口类型不做泛型。需要更复杂逻辑通常说明算子该拆了

## 实施要点

- 前端把 manifest 存在独立 store，节点渲染时按 `op` **现查**，不要在创建节点时把 manifest 快照进节点里
  （否则热重载失效，这个决定后期改代价很大）
- 参数迁移逻辑放 C++，不放前端，否则 headless 路径走不到迁移
