# xyz-gap-inspector 接入指南

本页说明间隙与段差业务宿主如何使用 LyFlow 的现有接口，以及平台与宿主的职责边界。平台能力以 [嵌入指南](embedding.md)、[图数据模型](graph-doc.md)、[gap 算子包](../packs/gap/README.md) 和 [HTTP 契约](http-transport.md) 为准；本页不表示外部业务仓库已经完成迁移。

## 职责分工

| LyFlow 提供 | 业务宿主负责 |
|---|---|
| core 执行器、缓存、事件、诊断与公共 C ABI | PLC、相机、采集调度、工件/帧身份及异常恢复 |
| 点云、推理和 gap 算子，参数与端口契约 | 产品规格、工况、判定、CSV/数据库字段与 PLC 回写 |
| GraphDoc、图参数、配方、命名输出和导入器 | 配置目录、模板/模型资产、数据库迁移、权限与发布事务 |
| C++ / Rust 客户端、React 编辑器和 Transport | 进程/线程模型、HTTP 服务、业务页面、部署及生产验收 |

测量算法在 LyFlow 算子包中维护，业务代码消费结果、装配场景和管理采集。设备标定、模板采集与裁剪等业务能力应按各自职责保留，不能为了替换测量调用而机械删除。

## 运行库与 SDK

C++ 宿主通过 `lyflow/client.hpp` 加载 core；Rust 宿主通过 `lyflow-client` 使用同一 C ABI。不要复制内部执行器或从业务代码直接依赖 core 内部结构。同步、异步句柄、取消、回调及运行结果的生命周期见 [嵌入指南](embedding.md)。

运行时兼容按产品版本的主、次系列判定，部署时统一使用交付包中的头文件、客户端和运行库依赖。Windows 客户端把第三方依赖搜索限制在指定 DLL 所在目录，不能依赖当前目录或 PATH 补齐缺失 DLL。包布局、源码修订与版本声明规则见 [发包指南](deployment/packaging.md)。

core 的并发能力不替代宿主的采集调度。每个并发运行应保留独立输入、runId、事件归属、输出读取及释放上下文；同一设备或工件是否串行由业务决定。进程内原生崩溃可能影响整个服务进程，需要隔离时由宿主设计进程边界与恢复策略。

## 图、配置与资源路径

每个测点可保存一张 `.lyflow.json`，测点启用、设备位置、别名和业务分类等元数据由宿主管理。图中只记录节点、算子版本、连线、参数与声明的输出，不写入当前选择、运行状态或业务数据库会话。

建议将图与其引用的模板、标定等资源作为可整体复制的配置单元：

```text
<point>/
  <point>.lyflow.json
  templates/
  ...宿主自己的测点元数据...
```

Path 参数相对图文件所在目录解析。每次验证、计划和执行都应传入同一个正确的 `baseDir`；工作流复制到另一目录后，不应仍依赖原进程的当前目录。发布前检查模型、模板和外部库是否可用。

宿主可以使用已注册的文本导入器转换旧配置。导入后须执行当前 core 的验证，核对参数单位、端口、图参数和资源路径，再以可回滚的业务事务保存。数据库版本、目录移动、历史数据转换和废弃业务接口的删除属于宿主工程，不由 LyFlow 自动完成。

算子迁移诊断与业务数据库迁移是两件事。宿主须区分警告、执行错误和明确的迁移建议，保存前核对变更；不能把任意诊断当作成功迁移或直接覆盖用户图。

## 输入与运行参数

生产采集可通过运行选项注入两片点云，无需先写临时 PCD。对于 `gap.read_scan`，向节点的 `primary`、`secondary` 输入注入传感器帧点云，两个输入齐备时使用它们，不再读配置目录。入口节点、端口与类型必须与图声明匹配，详细的输入注入和整节点输出注入区别见 [嵌入指南](embedding.md)。

点序、NaN 槽、RGB / 强度等通道按所用算子契约保留。模型定位需要原始有序剖面，不能为了方便提前删除 NaN 槽；gap 使用 RGB 的 R 通道携带强度，只注入 XYZ 可能改变模型路径结果。坐标帧与单位见 [gap 算子包](../packs/gap/README.md)。

图参数通过运行选项的 `params_json` 或对应客户端字段传入。编辑器、交互计算和批处理应使用同一套参数合成顺序；配方先做失配检查，明确哪些值来自图、配方或本次覆盖。不可应用的参数补丁应作为错误反馈，不能静默丢弃后继续报成功。规则见 [参数配方](recipe.md)。

与注入运行对应的计划和按节点缓存清理，应使用同一份输入；不带输入的计划不能代替那次注入运行的缓存判断。宿主记录输入、模型和标定身份，避免将同一路径下的新数据当作旧数据复用。

## 命名输出、执行结论与业务判定

GraphDoc 的顶层 `outputs` 将业务名称绑定到节点端口。宿主按约定读取 `gap`、`flush`、`bundle` 等名字，不依赖编辑器的节点顺序或临时 ID。未声明、不活动、失败和有效输出应分别处理，不能用零填补缺失测量。

执行结论读取 core 生成的 `summary.status`（`ok`、`degraded`、`failed`），不要自行从节点颜色或零散事件重建。缓存命中、未被 demand 的备用分支及被容错端口接住的上游错误都会影响解释。产品是否合格仍需独立检查量测有效性、质量信号和产品规格。

模型失败回退模板可由图中的 `flow.fallback` 表达。备用路径按需调度，未执行的备用节点不是执行失败。宿主需要保留回退选择和原因，不能把回退成功掩盖成主路径始终正常。

`gap.result_bundle` 输出 `Record<GapResultBundle>`，汇总量测、ROI、拟合、对齐、点数和回退信息；它不重新计算未接入的数据，也不保证旧业务结果结构中的每个字段都有值。当前字段与缺省语义以 [算子实现](../packs/gap/ops/result_bundle.cpp) 和 manifest 为准。

- `roi_source` 反映实际选中的定位/ROI 来源，不能由宿主文件名推断模型路径是否生效。
- 点数对应各输入实际提供的阶段；它们不一定等价于旧算法同名字段。未产出的逐阶段或逐圆诊断不得伪造为零或合格。
- `graph_sha256` 来自宿主传入的 `graphSha256` 参数，core 不自动替宿主计算配置包身份。宿主应明确该值标识的图文件及其序列化方式；运行时配方、参数覆盖、模型和输入身份另行记录，不能将原始图文件摘要误当成完整执行配置摘要。
- `pack_versions` 用于记录算子包版本。业务 CSV、`config_sha256` 等旧列的命名、保留或映射规则由宿主定义，不能无声明地改变列含义。
- `timings` 等历史兼容字段不能替代真实事件/summary 中的耗时。只读取生产需要的命名值；需要异常几何时再取相关输出或快照。

## 嵌入编辑器与服务

React 页面嵌入 `@lyflow/editor`，通过 `Transport` 对接宿主能力。HTTP 服务遵循 [HTTP 契约](http-transport.md)，不能只实现运行接口而遗漏结果、事件、图文件与库能力。Rust / Tauri 宿主也可复用现有桥接层，详见 [编辑器包](../packages/editor/README.md) 和 [嵌入指南](embedding.md)。

编辑器与宿主共用 React、React Flow、three 等 peer 依赖，防止重复实例造成上下文和渲染问题。一页只挂一个编辑器；切换多个工作流使用其标签会话，不能把同页多编辑器误当作独立实例隔离。

宿主传入 `topologyLocked` 时，节点结构不可改，参数、配方、运行、参数面板和日志仍可使用。主题通过现有变量覆盖，宿主自己保留业务结论、模板工具和操作权限。文件读写、保存确认及配置发布由对应宿主接口落实，不依赖开发期测试桥。

## 业务迁移与验收

迁移顺序应由宿主当前代码与数据库版本确定，不沿用已失效的旧分支路径或一次性删除清单。至少分别检查：

1. 配置可导入、验证并往返保存；资源路径、单位、图参数和配方含义明确；迁移中断能回滚，重新启动不会重复破坏配置。
2. 真实采集输入下命名输出、回退、量测缺失和执行失败映射正确；异常数据不会被静默写成正常结果。
3. 业务 UI 的编辑、重算、保存、历史查看和权限有效，CSV、数据库与 PLC 消费字段有契约。
4. 固定工件/帧划分与人工真值，分别验收量测误差、缺失率、产品误检漏检、定位失败与回退，不以旧算法逐位相同作为唯一正确性标准。
5. 同机测量冷/热缓存节拍、并发时延、吞吐和峰值资源；使用实际交付物验证依赖加载及故障恢复。

平台测试只能证明覆盖到的平台契约，不能替代业务真实数据、数据库迁移或现场准确率验收。业务验收应记录图、配置、输入、标定、运行库版本与源码修订，并保存未通过和未验证项；命令与测试分层见 [测试地图](testing.md)。
