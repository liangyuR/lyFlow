# 私有引擎与公共工具链拆仓计划

目标是让私有仓先独立发布 Windows x64 runtime 和原生 SDK，再让公共仓仅用已发布的产物构建 CLI 和桌面工具。完成的标志是外部开发者只克隆公共仓，能跑通 C++ 宿主、CLI、MCP 和桌面编辑器。发布物名称、构建入口与示例命令见[发包说明](packaging.md)。

## 两个仓库各自交付什么

| 归属 | 源码与职责 | 发布物 |
| --- | --- | --- |
| 私有引擎仓（建议名 `lyflow-engine`） | `core/`、`kernels/`、`packs/`、`solutions/`，原生依赖、算子注册、算法和领域测试。维护 C ABI 头文件、C++ 包装头、引擎理解的图与算子契约，以及随引擎运行的 Python worker 和协议 | 现有 runtime ZIP 与运行库 NuGet；独立的原生 SDK ZIP，包含配套运行库、头文件、导入库、已承诺的公共内核静态库、CMake 配置与原生宿主示例；随版本提供算子 manifest、公共 schema 和依赖许可 |
| 公共工具仓（建议沿用 `liangyuR/lyFlow`） | Rust 客户端、`bridge/` 中的 CLI 和桌面壳、编辑器、可视化、MCP、HTTP 桥接、公共宿主示例与面向用户的文档。按引擎导出的契约消费算子 | headless CLI、桌面工具、编辑器包和 MCP 工具。过渡期可将同版原生 SDK 与 CLI 组装成原有布局的完整 SDK ZIP，供已有下载脚本继续使用 |

私有仓的发布作业将允许分发的二进制和接口资产上传至公共仓构建者可读取的位置。建议保留现有公共 Release 和 NuGet 消费入口，按资产名区分原生 SDK 与含 CLI 的完整 SDK。同一 runtime 只构建一次。公开内容按文件清单挑选，尤其核对 SDK 示例、算法分析文档、测试数据和模型。原仓曾公开的历史版本仍可取得，新的专有算法提交从私有仓开始。

## 实施顺序与验收

| 步骤 | 改动 | 进入下一步的条件 |
| --- | --- | --- |
| 1. 在现仓拆开发包入口 | 从 `scripts/package-windows.ps1` 提取引擎发布步骤和工具组装步骤。梳理 `core/CMakeLists.txt` 跨目录安装的示例、文档、脚本及 Python 文件，给每件发布物指定唯一来源。把 CLI、MCP、桌面和依赖 CLI 的验收归到工具步骤 | 仅凭引擎侧文件即可产出 runtime、NuGet 和原生 SDK。外部 C++17 工程从解压目录执行 `find_package(lyflow … EXACT)`，链接并跑一张图。SDK 中的 DLL 与同版 runtime 身份一致 |
| 2. 让公共工具真正使用预编译产物 | 调整 `bridge/build.rs`，先处理已发布运行库。现有 `LYFLOW_PREBUILT_CORE_DIR` 分支之前就要求相邻的 `core/` 存在，之后还会读取其中的 UTF-8 程序清单。将 exe 所需清单移到工具侧，窗口打包和 Python 资源暂存改从各自的发布输入取；梳理 Rust 测试的编译期示例引用 | 在仅含公共文件、没有私有仓凭据的干净 Windows runner 上，按锁定版本下载资产；构建 CLI、桌面与 MCP，无需原生源码、vcpkg 或原生引擎编译缓存 |
| 3. 分配 CI 和发布权限 | 私有 CI 保留原生算法、ABI、完整依赖与原生 SDK 消费验证。公共 CI 验 Rust 封送、CLI 退出码、MCP 取数和真实桌面交互。私有发布作业持有上传二进制的权限，公共构建只需读取已发布资产。按运行库版本锁定目标平台、下载位置、资产摘要和引擎修订 | 从公共 CI 构建出的 CLI 执行 `info`、`manifest --check` 并跑一张公开图；MCP 读到该图的实际结果。将桌面产物放进干净目录，验证通过 Tauri 加载配套 DLL，显示同一图的算子与输出。提供错误 ABI 或缺少 DLL 时，现有诊断能定位原因 |
| 4. 切仓并演练首次双仓发布 | 从同一切点迁移职责。私有仓先发布引擎资产，公共仓通过依赖更新提交锁定该版本，验证通过后再发布工具。保留旧 tag、NuGet 包 ID 和已发布下载地址。工具修复可沿用上一版引擎 | 用正式下载入口分别复验原生宿主、公共 CLI/MCP 和桌面工具。用现有下游消费方式验证一次固定版本恢复，并完成一次回退演练 |

## 版本、失败与回退

- **版本与身份。** 构建固定完整引擎版本，运行时沿用现有主、次版本 ABI 兼容规则。原先以同一 Git 修订核对 Rust 客户端与运行库的约定，拆仓后改为公共工具修订对应明确的引擎版本、引擎修订与 ABI。DLL 和 NuGet 中的引擎身份始终指向私有引擎的构建。首次切换可以沿用同步版本号，两个仓的提交分别记录。
- **发布顺序。** 私有仓完成原生门禁并发布不可变资产，公共仓再更新依赖、构建和发布。公共工具门禁失败时，原有稳定工具继续使用先前锁定的引擎。修复后重跑公共流程即可。已对外发布的错误组合通过新工具补丁重新固定到已验证的引擎，保留旧产物以便复现。
- **首轮范围。** 沿用现有 Windows x64 与正式算子组合。实施前由维护者确认哪些领域二进制、头文件、示例和文档允许公开分发，以及公共工具的许可。若某个 solution 只允许授权客户获取，应当使用单独的受控发行渠道；公共 runner 只验可公开取得的组合。

## 当前实施范围

私有引擎已独立发包，公共工具可通过 `LYFLOW_NATIVE_SDK` 构建。原生 C++ 探针直接消费引擎头文件，并复用 SDK 的 Profile 宿主示例。私有源码位于 [lyflow-engine](https://github.com/liangyuR/lyflow-engine)。

首版双仓引擎 2.0.3 沿用全量算子组合及许可说明，对外分发范围包括 runtime ZIP、原生 SDK ZIP 和运行库 NuGet。[公共仓版本锁](../../packaging/engine-releases/v2.0.3.json)记录三件原始资产的正式下载地址、文件摘要与引擎修订。NuGet 发布流程按该修订验证原包。

## 首次双仓发行后的遗留计划

本地候选验收已在隔离检出中使用原生 SDK 构建 Release CLI、运行 MCP 测试，并启动真实 WebView2 桌面完成交互测试。本地 CLI 也已按 2.0.3 → 2.0.2 → 2.0.3 切换运行库，每次都读到对应引擎身份，同一示例图执行成功且结果一致。以下工作从公共发行渠道和下游实际安装方式继续验收。

| 顺序 | 公共仓工作 | 完成条件 |
| --- | --- | --- |
| 1. 补齐公共工具下载 | 双仓发布流程目前只将三件引擎资产放入 Release。用已锁定的原生 SDK 和公共仓构建的 Release CLI 组装完整 SDK ZIP，并打包同版编辑器 tarball。保留现有下载文件名及 CLI 所在目录。 | 在空目录下载完整 SDK，运行其中的 CLI，核对引擎身份并执行随包图。在外部 React 宿主安装 Release 中的编辑器 tarball，完成构建并打开示例图。 |
| 2. 把日常 CI 切到已发布 SDK，移除重复源码 | 发布作业已有只检出公共文件的构建路径，日常 PR 的 Rust 作业仍使用公共仓编译的 core。先将公共工具检查切到版本锁，核对私有 CI 已覆盖原生算法、ABI 和 SDK 消费，再从公共主分支移除原生实现、专用依赖脚本及重复门禁。保留工具使用的示例和说明。 | 干净 Windows runner 只检出公共仓，无私有仓凭据和原生编译缓存，能恢复 SDK、构建 CLI / MCP / 桌面并通过工具测试。公开示例、包说明与历史 Release 下载地址仍可使用。 |
| 3. 用正式渠道复验桌面和下游回退 | 复用候选验证的示例与桌面场景。通过 Release 下载 ZIP，通过配置好的 GitHub Packages 源按精确版本恢复 NuGet。选取一个实际下游宿主，按其部署方式演练升级与回退。 | 外部 C++17 工程通过 `find_package(lyflow … EXACT)` 构建并运行；在新目录启动桌面，核对 DLL 身份并查看示例图的输出；CLI 与 MCP 能读到同图结果。下游宿主切换到新包、回到原验收版本、再恢复新包，每次均记录实际加载版本与示例执行结果。缺 DLL 或 ABI 不兼容时能定位加载失败原因。 |
| 4. 更新开发指南与路线图 | 将 README 和快速开始的默认路径改为从版本锁恢复 SDK，把原生开发入口指向引擎仓。在测试地图中标明门禁归属，修正路线图里仍把已交付的算子包迁移列为规划的条目。 | 从全新公共检出按文档即可运行首张图。开发者能找到公共工具和原生引擎各自的测试入口，以及仍需业务宿主独立验收的项目。 |
